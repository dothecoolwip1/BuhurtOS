Optimization

1. Screens load on first open (frontend)

The whole site was one 2 MB script that every phone downloaded and parsed before showing anything. Each screen now loads when it is first opened (src/lib/lazyPage.ts, src/App.tsx).

Measured in Chromium at 390×844, median of 3 runs, time until the screen is usable:

ScreenSlow 3G before → afterFast 3G before → after
Home6.7 s → 2.8 s3.4 s → 1.6 s
Counter6.6 s → 3.4 s3.4 s → 2.0 s
Event Control6.7 s → 2.8 s3.4 s → 1.6 s

Script needed for the first screen: 1,976 KB → about 650 KB (Event Control 1,258 KB).

Safety, tested in a real browser (scripts/e2e/lazy-chunks.mjs):

  • After a deploy, a tab still running the old build opens a screen whose file is gone. It reloads once onto the new build and shows that screen. It never reloads in a loop.
  • Offline, after one visit the offline worker has every screen. A phone with no signal can open screens it has never opened.
  • vercel.json no longer rewrites missing /assets/* files to the app page, so a missing file fails cleanly.

2. Counter and Lyst desk polls (database)

Hosted evidence (read-only):

  • pg_stat_statements since 2026-10-10: counter_state averaged 433 ms over 8,108 calls; lyst_state averaged 248 ms over 10,359.
  • Edge logs, last 24 h: counter_state p95 4.6 s, max 12.7 s, 28 errors (5xx); lyst_state p95 4.4 s, 15 errors; device_whoami p95 13.7 s; device_refresh_session p95 16.8 s.
  • Postgres logs: 69 "canceling statement due to statement timeout" between 19:24 and 19:56 UTC on 30 Oct, inside counter_state and lyst_state.

Cause: the 28 one-statement helpers these polls call were SQL-language SECURITY DEFINER functions. PostgreSQL never inlines those and plans their statement again on every call, many times per poll. Migration 20261115000100_counter_poll_cost.sql keeps each statement unchanged and runs it as PL/pgSQL, whose plans are cached per connection. counter_state_for also reads the Lyst list and the current fight once instead of twice each.

Correctness: hosted definitions of all 32 functions were compared by hash with the repository first (identical). Then every counter session's state, every Lyst's state, and every converted helper for every event, Lyst, fight and entry were compared before and after: identical (2,989 rows; clock fields excluded, synthetic ties in finish times broken first because the "last fight" pick among fights finished at the same instant is arbitrary in both versions).

The migration only replaces functions; no rows change, so open events, Lysts, fights and counter phones pick it up on their next poll. It is not applied to hosted. That needs Garrett's go.

3. Hosted compute (needs Garrett)

The local per-poll cost is about 8 ms; hosted takes hundreds of ms and times out at peak. The hosted project is on the smallest compute (Micro: 60 connections, 224 MB shared buffers), and the same database also serves the steeltape game. The slowness on 30 Oct is the machine running out of CPU, so the migration helps but a bigger machine is the direct fix for tournament weekends.

Step by step (Supabase website):

  1. Open https://supabase.com/dashboard/project/mvbxlebznlgroptwwdsm/settings/compute-and-disk
  2. Under Compute size, the current value is Micro. Choose Small.
  3. Read the price the page shows, then click Confirm (or Save changes).
  4. The database restarts for about two minutes. Do it when no fight is running. To go back later, repeat with Micro.
